# Local CONNECT proxy in front of the Resolver webview

animepahe.pw sits behind a Cloudflare JS challenge: a plain HTTP client gets a 403 "Just a moment" page, so resolution requires a real browser engine. On some ISPs the domain's DNS is also poisoned, and a webview cannot override per-host DNS the way Chrome's `--host-resolver-rules` can. We therefore run a local HTTP CONNECT proxy inside the app that resolves every requested hostname through DoH (Cloudflare JSON API, `1.1.1.1` fallback), and attach it to the Resolver webview with Tauri's `proxy_url`. The proxy starts only when a TLS probe against the Base URL returns a certificate mismatch (a poisoned resolver); settings can force it on or off. wry implements that per platform: `WKWebsiteDataStore.proxyConfigurations` on macOS (requires the `macos-proxy` feature), WebView2 `--proxy-server` on Windows, WebKitGTK `NetworkProxySettings` on Linux. TLS stays end-to-end; the proxy only tunnels bytes and never intercepts certificates.

Rejected alternatives: changing system DNS (global and invasive), an `/etc/resolver` daemon (needs root), a bundled Chrome/patchright sidecar (bundle weight), and curl-impersonate (cannot execute the JS challenge).

Consequences: resolution depends on DoH only when the proxy is active; clean networks never start it; on Linux the proxy attaches to the shared `WebContext`, so it is app-wide rather than per-webview; the UI is served from a custom scheme, so it never traverses the proxy.
